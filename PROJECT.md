# PROJECT.md
## Веб-приложение «БрифМастер AI»

---

## 1. Общее описание проекта

«БрифМастер AI» — это адаптивное веб-приложение для UX/UI-дизайнеров, разработчиков сайтов, фрилансеров и небольших веб-студий.

Приложение превращает неструктурированное сообщение клиента, переписку или заметки после созвона в понятный бриф на разработку сайта.

Приложение:

- открывается в браузере на компьютере, планшете или телефоне;
- не требует регистрации и авторизации в первой версии;
- использует искусственный интеллект для анализа текста;
- позволяет выбрать одного из двух AI-провайдеров: **OpenRouter** или **OpenAI API**;
- не требует от пользователя ввода собственного API-ключа;
- хранит ключи владельца приложения только на сервере;
- не использует базу данных в MVP;
- публикуется на Vercel и доступно по обычной ссылке.

Основная идея:

> от хаотичного сообщения клиента → к структурированному брифу → к понятному плану разработки сайта.

---

## 2. Проблема пользователя

Клиенты часто описывают будущий сайт в свободной форме: присылают длинные сообщения, разрозненные пожелания, голосовые заметки после расшифровки или фрагменты переписки.

Дизайнеру или разработчику приходится вручную:

- выделять главную цель проекта;
- определять целевую аудиторию;
- составлять структуру сайта;
- собирать функциональные требования;
- фиксировать пожелания по дизайну;
- выявлять недостающую информацию;
- составлять уточняющие вопросы;
- формировать последовательность дальнейшей работы.

«БрифМастер AI» сокращает эту ручную работу и формирует первоначальный структурированный документ за один запрос.

## 6. Основной сценарий работы

1. Пользователь открывает приложение.
2. Выбирает AI-провайдера: OpenRouter или OpenAI.
3. Вставляет сообщение клиента или описание проекта.
4. Нажимает кнопку «Сформировать бриф».
5. Приложение проверяет введённый текст.
6. Показывает индикатор загрузки и блокирует повторную отправку.
7. Клиентская часть отправляет текст и название выбранного провайдера в серверный Route Handler.
8. Сервер выбирает соответствующий API-ключ из защищённых переменных окружения.
9. Сервер отправляет запрос выбранному AI-провайдеру.
10. AI анализирует сообщение и формирует структурированный бриф.
11. Приложение показывает результат по отдельным разделам.
12. Пользователь копирует результат или очищает форму.

---

## 7. Режим выбора AI-провайдера

### Назначение

Пользователь может выбрать сервис, который сформирует бриф.

Доступные варианты:

- **OpenRouter** — основной провайдер;
- **OpenAI API** — альтернативный провайдер.

### Логика работы

- По умолчанию выбран OpenRouter.
- Пользователь может переключиться на OpenAI до отправки запроса.
- Пользователь не видит и не вводит API-ключи.
- Выбранный провайдер передаётся на сервер вместе с исходным текстом.
- Независимо от провайдера результат должен иметь одинаковую структуру.
- При ошибке приложение сообщает, какой провайдер не смог обработать запрос.
- Автоматическое переключение на другого провайдера без уведомления пользователя не выполняется.

## 8. Режим ввода исходного текста

### Назначение

Поле предназначено для вставки исходной информации от клиента.

Пользователь может вставить:

- сообщение клиента;
- переписку;
- ответы на вопросы;
- заметки после созвона;
- расшифровку голосового сообщения;
- свободное описание будущего сайта.

### Возможности

- Ввести или вставить текст
- Увидеть подсказку с примером подходящего содержания
- Отправить текст на обработку
- Сохранить введённый текст на экране при технической ошибке
- Очистить поле вручную

### Валидация

- Пустой текст не отправляется.
- Слишком короткий текст сопровождается просьбой добавить информацию.
- Слишком длинный текст не отправляется и сопровождается понятным сообщением.
- Проверка выполняется и в браузере, и повторно на сервере.

---

## 9. Режим формирования брифа

### Назначение

Искусственный интеллект анализирует исходный текст и преобразует его в рабочий бриф.

### Структура результата

AI должен формировать 11 разделов:

1. Общая информация о проекте
2. Цель сайта
3. Целевая аудитория
4. Тип сайта
5. Предлагаемая структура сайта
6. Функциональные требования
7. Пожелания по дизайну
8. Необходимые интеграции
9. Материалы, которые должен предоставить клиент
10. Вопросы для уточнения
11. Рекомендуемый порядок работы

### Правила работы AI

- Не придумывать факты, которых нет в исходном сообщении.
- Явно отмечать отсутствующую информацию.
- Переносить недостающие сведения в раздел «Вопросы для уточнения».
- Отделять факты клиента от рекомендаций AI.
- Использовать понятный профессиональный русский язык.
- Не дублировать одну и ту же информацию в нескольких разделах без необходимости.
- Возвращать одинаковую структуру независимо от выбранного провайдера.

## 10. Сущность: BriefRequest (Запрос на создание брифа)

Поля:

- `text: string` — исходный текст пользователя
- `provider: "openrouter" | "openai"` — выбранный AI-провайдер

Пример типа TypeScript:

```typescript
type AIProvider = "openrouter" | "openai";

type BriefRequest = {
  text: string;
  provider: AIProvider;
};
```

---

## 11. Сущность: Brief (Готовый бриф)

Поля:

- `projectOverview` — общая информация о проекте
- `siteGoal` — цель сайта
- `targetAudience` — целевая аудитория
- `siteType` — тип сайта
- `siteStructure[]` — предлагаемая структура сайта
- `functionalRequirements[]` — функциональные требования
- `designPreferences[]` — пожелания по дизайну
- `integrations[]` — необходимые интеграции
- `requiredMaterials[]` — материалы от клиента
- `clarificationQuestions[]` — вопросы для уточнения
- `recommendedWorkflow[]` — рекомендуемый порядок работы

Пример типа TypeScript:

```typescript
type Brief = {
  projectOverview: string;
  siteGoal: string;
  targetAudience: string;
  siteType: string;
  siteStructure: string[];
  functionalRequirements: string[];
  designPreferences: string[];
  integrations: string[];
  requiredMaterials: string[];
  clarificationQuestions: string[];
  recommendedWorkflow: string[];
};
```

## 12. Интерфейс приложения

Приложение состоит из одной основной страницы.

### Верхняя часть

- Название «БрифМастер AI»
- Краткое описание назначения приложения
- Пояснение, что текст обрабатывается выбранным AI-провайдером

### Форма

- Переключатель OpenRouter / OpenAI
- Большое многострочное поле для текста клиента
- Подсказка по заполнению
- Сообщение валидации
- Кнопка «Сформировать бриф»
- Кнопка «Заполнить примером» — дополнительная функция

### Область результата

- Индикатор «Формируем бриф…»
- Сообщение об ошибке при неудачном запросе
- Одиннадцать разделов готового брифа
- Кнопка «Скопировать результат»
- Уведомление «Бриф скопирован»
- Кнопка «Очистить»

### Адаптивность

- На компьютере форма и результат могут располагаться в две колонки при достаточной ширине.
- На планшете и телефоне все блоки располагаются последовательно в одну колонку.
- Кнопки должны быть удобны для нажатия пальцем.
- Текст не должен выходить за границы экрана.
- Страница должна сохранять понятную иерархию при любом размере экрана.

## 13. Состояния интерфейса

Приложение должно поддерживать следующие состояния:

1. **Начальное** — поле пустое, результат отсутствует.
2. **Заполненное** — текст введён, можно отправить запрос.
3. **Ошибка валидации** — показано сообщение о проблеме с текстом.
4. **Загрузка** — отображается индикатор, кнопка отправки заблокирована.
5. **Успешный результат** — показаны все разделы брифа.
6. **Ошибка API** — исходный текст сохранён, показано понятное сообщение.
7. **Результат скопирован** — показано краткое уведомление.
8. **Очищено** — форма и результат возвращены в начальное состояние.

---

## 14. Серверная часть и API

Для обращения к AI используется серверный Route Handler Next.js.

Предполагаемый маршрут:

```text
POST /api/generate-brief
```

Сервер получает:

- исходный текст;
- выбранного провайдера.

Сервер выполняет:

1. Проверку метода и входных данных.
2. Проверку допустимого значения провайдера.
3. Выбор соответствующего серверного API-ключа.
4. Формирование системной инструкции для AI.
5. Отправку запроса провайдеру.
6. Проверку ответа.
7. Приведение результата к единому формату `Brief`.
8. Возврат результата клиентской части.

---

## 15. Безопасность API-ключей

Используются два ключа владельца приложения:

- `OPENROUTER_API_KEY`
- `OPENAI_API_KEY`

Правила безопасности:

- Ключи хранятся в `.env.local` при локальной разработке.
- На Vercel ключи хранятся в разделе Environment Variables.
- `.env.local` не отправляется в GitHub.
- Ключи используются только в серверном Route Handler.
- Ключи запрещено добавлять в переменные с префиксом `NEXT_PUBLIC_`.
- Ключи не передаются в клиентские компоненты.
- Ключи не возвращаются в ответах API.
- Ключи не выводятся в консоль и журналы.
- Сообщения об ошибках не должны содержать ключ или полный технический ответ провайдера.

## 16. Ограничение расходов и защита от злоупотреблений

Поскольку запросы оплачивает владелец приложения, необходимо предусмотреть:

- ограничение максимальной длины исходного текста;
- ограничение максимального размера ответа AI;
- блокировку повторного нажатия во время выполнения запроса;
- ограничение частоты запросов;
- проверку входных данных на сервере;
- понятное сообщение при достижении лимита;
- контроль расходов в кабинетах OpenRouter и OpenAI;
- возможность временно отключить одного из провайдеров.

Для хакатонного MVP достаточно базовой защиты от частых повторных запросов. Более сложная система квот относится к дальнейшему развитию.

---

## 17. Обработка ошибок

Приложение должно показывать понятные сообщения в следующих случаях:

- поле не заполнено;
- текст слишком короткий;
- текст превышает допустимый объём;
- выбран неизвестный провайдер;
- отсутствует серверный API-ключ;
- AI-провайдер временно недоступен;
- превышено время ожидания;
- получен некорректный ответ;
- превышен лимит запросов;
- отсутствует подключение к интернету.

Исходный текст пользователя не должен исчезать при ошибке API.

---

## 18. Хранение данных

В обязательном MVP:

- база данных не используется;
- исходный текст не сохраняется на сервере;
- готовый бриф не сохраняется на сервере;
- история запросов не передаётся между устройствами;
- после обновления страницы несохранённые данные могут быть потеряны.

Дополнительно, если основная версия полностью готова:

- несколько последних брифов можно сохранять в `localStorage` браузера;
- пользователь может просматривать и удалять локальную историю;
- в `localStorage` никогда не сохраняются API-ключи.

## 19. Критерии готовности MVP

Приложение считается готовым, если:

- открывается по публичной ссылке;
- работает без регистрации;
- пользователь может выбрать OpenRouter или OpenAI;
- пользователь не вводит API-ключ;
- пустой и некорректный текст не отправляется;
- запрос выполняется только через серверный Route Handler;
- оба провайдера могут сформировать бриф;
- результат содержит 11 заданных разделов;
- отсутствующая информация не выдумывается;
- результат можно скопировать;
- форму и результат можно очистить;
- загрузка и ошибки отображаются понятно;
- интерфейс работает на компьютере и телефоне;
- ключи отсутствуют в GitHub и клиентском коде;
- `npm run lint` завершается без ошибок;
- `npm run build` завершается без ошибок;
- приложение успешно опубликовано на Vercel.
