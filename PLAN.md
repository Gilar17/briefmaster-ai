# PLAN.md

## План разработки MVP веб-приложения «БрифМастер AI»

Документ полностью опирается на `PROJECT.md` и не расширяет продукт за пределы утверждённого описания. Это рабочий план на семь дней для одного начинающего разработчика с помощью Cursor.

Главный приоритет: сначала полностью работающий и проверенный обязательный MVP, затем дополнительные функции только при наличии свободного времени.

---

## 1. Название проекта

**БрифМастер AI**

Репозиторий и npm-пакет: `briefmaster-ai`.

---

## 2. Краткое описание

«БрифМастер AI» — адаптивное веб-приложение для UX/UI-дизайнеров, веб-дизайнеров, разработчиков сайтов на Tilda, frontend-разработчиков, фрилансеров, менеджеров веб-проектов и небольших веб-студий.

Пользователь вставляет неструктурированное сообщение клиента, переписку, заметки после созвона или расшифровку голосового сообщения. После нажатия кнопки «Сформировать бриф» приложение отправляет текст выбранному AI-провайдеру и показывает структурированный бриф на разработку сайта из 11 разделов.

Приложение поддерживает двух AI-провайдеров:

1. OpenRouter — основной, выбран по умолчанию.
2. OpenAI API — альтернативный.

Пользователь выбирает провайдера в интерфейсе, но не вводит собственный API-ключ. Используются два серверных ключа владельца приложения. Регистрация, база данных и личный кабинет в MVP отсутствуют.

Основная идея:

> от хаотичного сообщения клиента → к структурированному брифу → к понятному плану разработки сайта.

---

## 3. Цель проекта

За семь дней создать небольшой, понятный и безопасный MVP, который:

- быстро преобразует сообщение клиента в структурированный бриф;
- помогает дизайнеру не пропускать важные требования;
- отделяет известные факты от отсутствующей информации;
- автоматически составляет вопросы для уточнения;
- предлагает предварительную структуру сайта;
- формирует понятный порядок дальнейшей работы;
- позволяет выбрать OpenRouter или OpenAI;
- даёт возможность скопировать результат;
- публикуется на Vercel и открывается по обычной ссылке без регистрации.

Проект должен демонстрировать один полностью работающий сценарий и быть готовым к показу на хакатоне.

## 4. Проблема пользователя

Клиенты часто присылают требования к сайту в виде длинных сообщений, свободного описания, разрозненных пожеланий, фрагментов переписки или расшифровок голосовых заметок.

Дизайнеру или разработчику приходится вручную:

- выделять цель проекта;
- определять целевую аудиторию;
- составлять структуру сайта;
- собирать функциональные требования;
- фиксировать пожелания по дизайну;
- определять необходимые интеграции;
- составлять список материалов от клиента;
- выявлять отсутствующие сведения;
- формировать уточняющие вопросы;
- определять порядок дальнейшей работы.

«БрифМастер AI» автоматизирует первоначальную обработку сообщения клиента и выдаёт готовую основу брифа за один запрос.

### Планируется использовать без усложнения стека

- OpenAI API через серверный `fetch`;
- `localStorage` только для необязательной локальной истории после готовности MVP;

- база данных;

## 8. Основной пользовательский сценарий

1. Пользователь открывает приложение в браузере.
2. Выбирает OpenRouter или OpenAI. Если ничего не меняет, остаётся OpenRouter.
3. Вставляет сообщение клиента, переписку, заметки или расшифровку.
4. Нажимает кнопку «Сформировать бриф».
5. Приложение проверяет, что текст не пустой, не слишком короткий и не слишком длинный.
6. Показывает индикатор «Формируем бриф…».
7. Блокирует повторную отправку, пока запрос выполняется.
8. Клиентская часть отправляет на сервер только `text` и `provider`.
9. Сервер повторно проверяет входные данные и допустимое значение `provider`.
10. Сервер выбирает соответствующий API-ключ из переменных окружения.
11. Сервер отправляет запрос выбранному AI-провайдеру с общей системной инструкцией.
12. AI возвращает структурированный результат.
13. Сервер проверяет ответ и приводит его к единому типу `Brief`.
14. Приложение выводит бриф по 11 разделам.
15. Пользователь копирует результат или очищает форму.

При ошибке исходный текст остаётся на экране. Автоматическое переключение на другого провайдера без уведомления пользователя не выполняется.

## 11. Выбор AI-провайдера

Зафиксированная логика:

- по умолчанию выбран OpenRouter;
- пользователь может выбрать OpenAI до отправки запроса;
- пользователь не видит и не вводит собственный API-ключ;
- интерфейс передаёт на сервер только текст и значение `provider`;
- допустимые значения `provider`: `openrouter` и `openai`;
- сервер проверяет значение `provider` и отклоняет любые другие строки;
- сервер выбирает соответствующий ключ: `OPENROUTER_API_KEY` или `OPENAI_API_KEY`;
- сервер выбирает конфигурацию соответствующего провайдера, включая фиксированную модель;
- результат обоих сервисов приводится к одному типу `Brief`;
- при ошибке приложение сообщает, какой сервис не смог обработать запрос;
- автоматическое переключение на другого провайдера без уведомления пользователя не выполняется;
- выбор конкретной модели пользователем в MVP не предусмотрен;
- модели задаются только на сервере и не показываются как отдельная настройка в интерфейсе;
- если один провайдер временно отключён владельцем, пользователь получает понятное сообщение и может выбрать другого провайдера самостоятельно.

## 12. Структура результата AI

AI всегда формирует ровно 11 разделов. Новые разделы добавлять нельзя.

| № | Раздел | Поле типа `Brief` | Формат |
| --- | --- | --- | --- |
| 1 | Общая информация о проекте | `projectOverview` | строка |
| 2 | Цель сайта | `siteGoal` | строка |
| 3 | Целевая аудитория | `targetAudience` | строка |
| 4 | Тип сайта | `siteType` | строка |
| 5 | Предлагаемая структура сайта | `siteStructure` | массив строк |
| 6 | Функциональные требования | `functionalRequirements` | массив строк |
| 7 | Пожелания по дизайну | `designPreferences` | массив строк |
| 8 | Необходимые интеграции | `integrations` | массив строк |
| 9 | Материалы, которые должен предоставить клиент | `requiredMaterials` | массив строк |
| 10 | Вопросы для уточнения | `clarificationQuestions` | массив строк |
| 11 | Рекомендуемый порядок работы | `recommendedWorkflow` | массив строк |

Если сведений нет, раздел не удаляется. В текстовых полях указывается, что информация отсутствует. В списках допускается пункт о том, что данные не указаны, а вопросы по пробелам переносятся в `clarificationQuestions`.

## 13. Правила работы AI

Единая системная инструкция используется для OpenRouter и OpenAI.

Правила:

- не придумывать сведения, которых нет в исходном тексте;
- явно отмечать отсутствующую информацию;
- добавлять вопросы по отсутствующим сведениям в раздел «Вопросы для уточнения»;
- отделять факты клиента от рекомендаций AI;
- не дублировать одинаковую информацию без необходимости;
- использовать понятный профессиональный русский язык;
- возвращать одинаковую структуру независимо от провайдера;
- не добавлять разделы, которых нет в утверждённой структуре;
- не возвращать API-ключи или технические данные;
- не включать Markdown-код в обычный результат брифа без необходимости;
- не комментировать внутреннюю реализацию приложения;
- не отвечать на запросы, не связанные с формированием брифа на разработку сайта.

Сервер должен запрашивать ответ в машиночитаемом JSON, соответствующем типу `Brief`, а на экране показывать обычный читаемый бриф без служебной разметки.

## 14. Типы данных TypeScript

Рабочий код типов сейчас не пишется. Ниже зафиксированы назначение и состав основных типов. Реализация планируется в `src/types/brief.ts` и в состоянии клиентской формы.

### 14.1. `AIProvider`

```typescript
type AIProvider = "openrouter" | "openai";
```

Назначение: допустимые значения выбранного провайдера. Используется в форме, в теле запроса и в серверной проверке.

### 14.2. `BriefRequest`

```typescript
type BriefRequest = {
  text: string;
  provider: AIProvider;
};
```

Назначение: данные, которые клиент отправляет на `POST /api/generate-brief`. Никакие ключи, модели и служебные настройки в этот тип не входят.

### 14.3. `Brief`

```typescript
type Brief = {
  projectOverview: string;
  siteGoal: string;
  targetAudience: string;
  siteType: string;
  siteStructure: string[];
  functionalRequirements: string[];
  designPreferences: string[];
  integrations: string[];
  requiredMaterials: string[];
  clarificationQuestions: string[];
  recommendedWorkflow: string[];
};
```

Назначение: единый формат готового брифа для обоих провайдеров, серверного ответа и отображения на странице.

### 14.4. `APIError`

Планируемый тип ответа при ошибке, без секретов и без трассировки:

```typescript
type APIError = {
  error: string;
  code:
    | "VALIDATION_EMPTY"
    | "VALIDATION_TOO_SHORT"
    | "VALIDATION_TOO_LONG"
    | "UNKNOWN_PROVIDER"
    | "PROVIDER_DISABLED"
    | "MISSING_API_KEY"
    | "OPENROUTER_UNAVAILABLE"
    | "OPENAI_UNAVAILABLE"
    | "TIMEOUT"
    | "INVALID_AI_RESPONSE"
    | "RATE_LIMIT"
    | "NETWORK";
};
```

Назначение: безопасный контракт ошибки между сервером и интерфейсом. Поле `error` содержит текст для пользователя. Поле `code` помогает интерфейсу выбрать формулировку, не раскрывая внутренности провайдера.

### 14.5. Состояние формы

Планируемые поля клиентского состояния:

- `text` — текущий текст в поле ввода;
- `provider` — выбранный провайдер, по умолчанию `"openrouter"`;
- `validationMessage` — сообщение клиентской проверки или пустая строка;
- `copied` — показано ли уведомление «Бриф скопирован».

Назначение: хранить ввод пользователя независимо от результата AI и не терять текст при ошибке.

### 14.6. Состояние выполнения запроса

Планируемые поля:

- `status` — `"idle" | "loading" | "success" | "error"`;
- `brief` — готовый `Brief` или `null`;
- `errorMessage` — понятный текст ошибки или пустая строка;
- `errorCode` — код ошибки или `null`.

Назначение: управлять загрузкой, блокировкой кнопки, показом результата и сообщений об ошибках.

### Что можно объединить в недельном MVP

Чтобы не усложнять структуру, допустимо:

- встроить `ProviderSelector`, `LoadingState` и `ErrorMessage` в `BriefForm.tsx` и `page.tsx`, если отдельные файлы мешают начинающему разработчику;
- хранить константы длины текста и лимита запросов в `src/lib/validation.ts`, не создавая лишние модули;
- не создавать отдельные хуки, контекст, стор и папку `hooks`, пока состояние умещается в одной странице.

Не следует создавать:

- `pages/` рядом с App Router;
- клиентские файлы, которые импортируют API-ключи;
- отдельные маршруты для OpenRouter и OpenAI;
- папку для базы данных;
- админ-страницы.

## 16. Серверный Route Handler

Планируется один основной маршрут:

```text
POST /api/generate-brief
```

Файл: `src/app/api/generate-brief/route.ts`.

### Входные данные

```json
{
  "text": "исходный текст клиента",
  "provider": "openrouter"
}
```

Допустимые значения `provider`: `openrouter`, `openai`.

### Последовательность работы сервера

1. Принять только метод `POST`. Остальные методы отклонить.
2. Прочитать тело запроса и проверить, что это объект с полями `text` и `provider`.
3. Проверить, что `provider` равен `openrouter` или `openai`.
4. Нормализовать текст: убрать лишние пробелы по краям.
5. Проверить, что текст не пустой, не слишком короткий и не слишком длинный.
6. Проверить базовый лимит частоты запросов в памяти процесса как дополнительную best-effort меру, без ожидания точного общего лимита на Vercel.
7. Проверить, не отключён ли выбранный провайдер.
8. Выбрать соответствующий серверный ключ.
9. Если ключ отсутствует, вернуть безопасную ошибку без названия переменной с секретом в открытом виде пользователю, но с понятным смыслом: сервис временно недоступен из-за настройки сервера.
10. Выбрать конфигурацию провайдера и фиксированную модель.
11. Сформировать запрос с общей системной инструкцией из `src/lib/ai/prompt.ts`.
12. Отправить запрос в OpenRouter или OpenAI с ограничением времени ожидания и максимального размера ответа.
13. Проверить HTTP-статус и содержимое ответа.
14. Разобрать JSON и привести его к типу `Brief`.
15. Если структура неполная, вернуть ошибку некорректного ответа.
16. Вернуть клиенту `{ brief: Brief }`.
17. Во всех ошибках не возвращать ключи, системную инструкцию, полный технический ответ провайдера и трассировку.

Клиентская часть вызывает только этот маршрут. Прямых запросов из браузера к OpenRouter и OpenAI быть не должно.

## 19. Ограничение расходов

Запросы оплачивает владелец приложения, поэтому в MVP нужна простая защита без тарифов, аккаунтов и пользовательских квот.

Основными мерами контроля расходов в недельном MVP являются:

1. **Ограничение длины исходного текста.** Предлагаемые значения для реализации: минимум 50 символов, максимум 8000 символов после обрезки пробелов. Точные числа фиксируются в `src/lib/validation.ts` и одинаково применяются на клиенте и сервере.
2. **Ограничение максимального размера ответа AI.** В запросах к провайдерам задаётся лимит выходных токенов, достаточный для 11 разделов, но не безграничный. Рекомендуемый ориентир: около 2000–3000 токенов.
3. **Блокировка повторной отправки во время загрузки.** Пока `status === "loading"`, кнопка «Сформировать бриф» неактивна, повторный `fetch` не запускается.
4. **Отсутствие автоматических повторных запросов.** При ошибке сети или провайдера приложение не делает скрытый retry.
5. **Отсутствие автоматического переключения на другого провайдера.** Если выбранный сервис не ответил, второй провайдер не вызывается скрыто.
6. **Серверная валидация.** Даже если клиентскую проверку обойти, сервер отклонит пустой, короткий, длинный или некорректный запрос.
7. **Базовое ограничение частоты запросов в памяти как дополнительная негарантированная мера.** Допустимый ориентир реализации: не больше 5 запросов с одного IP за 10 минут в памяти текущего серверного процесса. На Vercel это только базовая best-effort защита и не гарантирует точный общий лимит, потому что серверные экземпляры могут перезапускаться и выполняться параллельно. Если этот лимит сработал в текущем процессе, пользователю показывается понятное сообщение, например: «Слишком много запросов. Подождите несколько минут и попробуйте снова».
8. **Контроль бюджета и расходов в кабинетах OpenRouter и OpenAI.** Владелец приложения следит за балансом вручную. В сам MVP кабинет провайдера не встраивается.
9. **Установка доступных лимитов расходов у провайдеров.** Лимиты и предупреждения настраиваются в кабинетах OpenRouter и OpenAI, а не внутри приложения.
10. **Возможность временно отключить OpenRouter или OpenAI через серверные переменные окружения.** Без автоматического скрытого переключения.

В обязательный MVP не добавляются Redis, Upstash, база данных, сторонняя CAPTCHA, очереди, биллинг, тарифы, счета и сложная система квот.

## 20. Состояния интерфейса

Приложение состоит из одной страницы и должно поддерживать следующие состояния.

1. **Начальное состояние.** Поле пустое, выбран OpenRouter, результат отсутствует, ошибок нет, кнопка отправки доступна, но запрос не уходит из-за валидации пустого текста.
2. **Текст введён.** Поле заполнено допустимым текстом, можно нажать «Сформировать бриф».
3. **Ошибка валидации.** Показано сообщение о пустом, слишком коротком или слишком длинном тексте. Запрос к API не отправляется.
4. **Загрузка.** Показан индикатор «Формируем бриф…», кнопка отправки заблокирована, исходный текст остаётся в поле.
5. **Успешный результат.** Показаны все 11 разделов брифа, доступны копирование и очистка.
6. **Ошибка OpenRouter.** Исходный текст сохранён, показано сообщение, что OpenRouter сейчас не смог обработать запрос.
7. **Ошибка OpenAI.** Исходный текст сохранён, показано сообщение, что OpenAI сейчас не смог обработать запрос.
8. **Ошибка сети.** Исходный текст сохранён, показано сообщение об отсутствии соединения или сбое сети.
9. **Ошибка ограничения частоты запросов.** Исходный текст сохранён, показано предложение подождать и попробовать позже.
10. **Результат скопирован.** Кратко показано уведомление «Бриф скопирован».
11. **Форма очищена.** Текст, результат, ошибки и уведомление сброшены. Провайдер возвращается к OpenRouter. Это то же начальное состояние.

На широком экране форма и результат могут стоять в две колонки. На планшете и телефоне блоки идут друг за другом.

## 21. Валидация

Проверка выполняется дважды: в браузере до запроса и на сервере после получения тела.

### Клиентская проверка

- пустая строка или строка из пробелов не отправляется;
- текст короче минимума не отправляется;
- текст длиннее максимума не отправляется;
- `provider` может быть только `openrouter` или `openai`;
- во время загрузки повторная отправка невозможна.

### Серверная проверка

- метод только `POST`;
- тело должно содержать `text` и `provider`;
- `provider` строго равен `openrouter` или `openai`;
- текст снова проверяется на пустоту, минимум и максимум;
- неизвестный провайдер отклоняется даже при ручном запросе к API;
- слишком частые запросы отклоняются до вызова AI.

### Подсказка в поле ввода

Пользователю нужно объяснить, что можно вставлять:

- сообщение клиента;
- переписку;
- ответы на вопросы;
- заметки после созвона;
- расшифровку голосового сообщения;
- свободное описание будущего сайта.

## 22. Обработка ошибок

Пользователь видит короткие понятные формулировки на русском языке.

| Ситуация | Смысл сообщения |
| --- | --- |
| Поле не заполнено | Вставьте сообщение клиента или описание проекта. |
| Текст слишком короткий | Добавьте больше сведений, чтобы можно было собрать бриф. |
| Текст слишком длинный | Сократите текст. Сейчас он превышает допустимый объём. |
| Выбран неизвестный провайдер | Выберите OpenRouter или OpenAI. |
| Отсутствует серверный API-ключ | Выбранный сервис сейчас недоступен. Попробуйте позже или другого провайдера. |
| Провайдер отключён | Выбранный сервис временно отключён. Выберите другого провайдера. |
| OpenRouter временно недоступен | OpenRouter сейчас не смог сформировать бриф. Попробуйте позже или выберите OpenAI. |
| OpenAI временно недоступен | OpenAI сейчас не смог сформировать бриф. Попробуйте позже или выберите OpenRouter. |
| Превышено время ожидания | Запрос занял слишком много времени. Попробуйте ещё раз. |
| Получен некорректный ответ | Не удалось прочитать бриф. Попробуйте отправить запрос ещё раз. |
| Превышен лимит запросов | Слишком много запросов. Подождите несколько минут и попробуйте снова. |
| Нет подключения к интернету | Нет соединения с интернетом. Проверьте сеть и повторите попытку. |

Сообщения для пользователя не должны содержать:

- API-ключи;
- внутренние системные инструкции;
- полный ответ провайдера с техническими данными;
- трассировку ошибки;
- внутреннюю структуру сервера;
- имена файлов, стек вызовов и содержимое `.env.local`.

Исходный текст не очищается при ошибке API, сети, таймаута или лимита.

## 23. Адаптивность

Правила вёрстки:

- горизонтальная прокрутка страницы недопустима;

## 36. Основные риски и способы их уменьшения

| Риск | Как уменьшить |
| --- | --- |
| Утечка API-ключей | Хранить ключи только в `.env.local` и Vercel Environment Variables. Не использовать `NEXT_PUBLIC_`. Проверять Git, клиентский код, Network и ответы API по чек-листу безопасности. |
| Неконтролируемые расходы | Ограничить длину текста и размер ответа AI, блокировать повторную отправку, не делать автоматические повторы и скрытое переключение провайдера, валидировать запрос на сервере. Следить за бюджетом в кабинетах OpenRouter и OpenAI и включить доступные лимиты расходов у провайдеров. При необходимости временно отключить провайдера серверной переменной окружения. |
| OpenRouter недоступен | Показать ошибку именно OpenRouter. Дать пользователю самому выбрать OpenAI. Не переключать провайдера скрыто. |
| OpenAI недоступен | Показать ошибку именно OpenAI. Дать пользователю самому выбрать OpenRouter. |
| AI придумывает факты | Жёстко описать это в системной инструкции. Проверять на тексте с пробелами в данных. Требовать перенос неизвестного в «Вопросы для уточнения». |
| AI возвращает не JSON и не ту структуру | Просить JSON в инструкции, проверять поля на сервере, приводить к `Brief`, при несоответствии показывать ошибку некорректного ответа. |
| Разный формат у двух провайдеров | Использовать одну инструкцию, один тип `Brief` и одну функцию разбора ответа. |
| Слишком большой или пустой ввод | Валидировать на клиенте и сервере. |
| Превышение времени ожидания | Задать таймаут запроса, показать понятное сообщение, не запускать скрытый повтор. |
| Ограничение частоты на Vercel не гарантирует точный общий лимит | Лимит в памяти процесса — только базовая best-effort защита: экземпляры могут перезапускаться и работать параллельно. Для недельного MVP этого достаточно вместе с лимитами длины текста, размера ответа, блокировкой повторной отправки и лимитами расходов у провайдеров. Redis, Upstash, база данных, сторонняя CAPTCHA и сложная система квот в обязательный MVP не входят.
